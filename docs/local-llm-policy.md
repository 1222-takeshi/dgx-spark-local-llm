# ローカル LLM への委任方針

開発作業は **Spark のローカル LLM（作業者）** が行い、**クラウドの強いモデル（オーケストレーター。既定は Opus）** が計画・指示・レビュー・判定を行う。
モデルの性能と同時実行数の根拠は [operations.md](operations.md) と [results/](../results/RESULTS.md) に従う。各クライアントからの呼び出し方は #10 で追加する。

## 役割

| 役 | 担当 | やること | やらないこと |
|---|---|---|---|
| オーケストレーター | Opus（クラウド） | Issue・worktree の準備、作業指示（brief）、差分レビュー、commit・PR・merge の判断、難しい設計・不具合の判定 | 作業者が担える実装を黙って肩代わりする |
| 作業者 | Spark のローカル LLM | 実装、テストの実行、上流コードの調査、整形、下書き、一次レビュー | commit・push・PR・Issue 操作、worktree の外の編集、方針の決定 |

ローカルには T0（難問の司令塔）を置かない（[operations.md](operations.md)）。判断が割れるものはオーケストレーターが引き取る。

## 委任の流れ

1. オーケストレーターが Issue と専用 worktree を用意し、brief を書く。
2. 作業者は brief の範囲で worktree の中だけを編集し、検証コマンドを実行する。
3. 作業者は「返すもの」をまとめて終了する。
4. オーケストレーターが差分とログを確認し、採用・差し戻し・引き取りを決める。差し戻しは brief に追記して同じ作業者へ戻す。2 回の差し戻しで通らない場合、オーケストレーターがモデルの切替か引き取りを決め、理由を記録する。
5. 作業者が書いたコードを採用したときは、PR の説明に作業者（モデル名とクライアント）と差し戻しの回数を書く。

brief に書くもの:
- 目的と Issue 番号、編集してよいパス、触ってはいけないパス
- 完了条件（normal / edge / invalid / regression）と検証コマンド。検証コマンドはオーケストレーターが事前に実行して動くことを確かめる（誤ったコマンドは作業者の時間を大きく浪費する）
- 予算（時間・出力 tokens・tool 回数）

予算はクライアント側で強制する（時間は `timeout`、回数は `--max-turns` 等）。上限で止まった作業は途中の差分を採用せず、オーケストレーターが状態を確認して、範囲を絞った brief での差し戻しか引き取りを決める。

作業者が返すもの:
- 差分（未 commit のまま）、実行したコマンドと結果
- 所要時間・tokens・tool 回数（取れる範囲で）
- 未解決の点、推測で決めた点

## モデルと同時実行

- 既定は常駐の Ornith。コーディングが続く期間だけ Qwen3.8-27B へ切り替えてよい。切り替えはユーザーの承認を得てから、オーケストレーターかユーザーが [scripts/spark/](../scripts/spark/README.md) の手順で行う。事前に Ornith を使う他のサービスへの影響を確認する。作業者はモデルを切り替えない。同時に載せるのは 1 モデルだけ。
- 同時に動かす作業者の数は [operations.md](operations.md) の式で決める。既定は 4 本まで、長い入力を扱う作業者は 1〜2 本。
- 実行記録には、モデル名・思考の有無・上限 tokens・作業者を動かしたクライアント（Claude Code / Codex / opencode など）を残す。

## アクセスと秘密情報

- 呼び出しは Tailscale 内のゲートだけを使う。ポートやトンネルをインターネットへ公開しない。リクエストがクラウドを経由するクライアント設定に、私設の URL やトークンを渡さない。
- トークンは PC ごとに分けて発行し、各 PC のユーザー領域に権限 600 で置く。repo・ログ・Issue・brief・作業者への指示には書かない。漏れたらその PC のトークンだけを失効させる。
- repo の中ではホスト名を `<spark-host>` と書く。実名は各 PC の設定ファイルだけに置く。
- 作業者には、必要な worktree 以外の秘密情報・非公開データを渡さない。

## ベンチマークを作るとき

評価対象になりうるモデルに解答を作らせると、そのモデルの評価が有利に偏る。

- ローカル LLM に任せてよい: runner、Dockerfile、公開してよいテスト、検証スクリプト、上流の調査。
- オーケストレーター（と人）が書く: 参照修正、誤修正、隠しテスト、採点データ。作業者には見せない。
- 上のものと verification 記録の原本は repo の外（HDD 上のキャッシュ、権限 700）に置く。記録には作成者（モデル名か人）を残し、repo には公開してよい要約と SHA256 だけを置く。
- 作業者のクライアント設定で、この非公開ディレクトリと資格情報の読み取りを禁止する。

## ローカル LLM が使えないとき

- 黙ってクラウドのサブエージェントへ切り替えない。原因（ゲート停止、メモリ不足、モデル切替中など）を記録し、ユーザーに確認する。
- 例外: 接続基盤そのものの立ち上げ、方針・判定、ベンチマークの参照解はオーケストレーターが行う。
