## 3. 結論（現時点）

- ローカルに T0 は置かない。ローカル最高は 27B の 46（40K 思考）で、Sonnet の 55 に届かない。難問・設計はクラウドへ。
- 常駐の既定は Ornith（速く、長文脈と Tool Eval が安定）。コーディング重視なら 27B に切り替える。同時に載せるのは 1 モデルのみ。
- Gemma は思考なしの下書き（T2）、Nemotron は速い収集・整形（T2）。
- 思考ありの低スコアは大半が打切りで、誤答は少ない。上限を大きく取り、打切りを別集計する。
- Qwen3.8-Flash-Next は標準の vLLM 起動では 124GB で載らない。PLE テーブルを NVMe から mmap する方法で検証予定（下記）。

## 4. 運用メモ・落とし穴

- ハーネス: `runner.mjs`（基礎、openai バックエンドはストリーミング、`TIMEOUT_MS` で上限指定）、`code/code-runner.mjs`（コーディング、`--think`、`--max-tokens`、再開可能）。
- 非ストリーミングで 300 秒を超える応答は Node の fetch が切れ `fetch failed` になる（undici の headersTimeout）。ストリーミングにする。
- ランナーはエラー行も「完了」と数える。再実行前に jsonl からエラー行を除く。
- Mac のスリープで SSH トンネルが切れる。`caffeinate -i -s` で包み、`ServerAliveInterval` を付ける。
- 思考の切替は `chat_template_kwargs {enable_thinking, thinking, thinking_mode}`。
- Spark: 空きメモリを 15% 以上残す。Flash-Next を標準構成で起動してホストが停止した（重み合計 124GB）。
- 起動スクリプト（Spark の `~/work/`）: `ornith-run.sh`（既定）、`gemma-run.sh`、`nemotron-run.sh`、`flashnext-run.sh`（使わない）。27B は `~/work/dgx-spark-qwen38/run.sh`。
